# 縮小
<!-- summary: 失敗したケースが縮小される仕組み、ShrinkToとIntRangeTowardによる誘導、LetShrinkとNoShrink、SampleShrinkによる縮小の観察、失敗の種類が保たれる理由。 -->

ケースが失敗すると、pbtは同じ失敗をするもっと単純なケースを探し、そちらを報告します。
この探索はすべての生成器について自動で働きます。
`Custom`、`Map`、`Bind` で自分が書いた生成器も含みます。
「単純」が何を意味するか、探索をどう導くか、探索が何をしないかを説明します。

## ケースが縮む仕組み

プロパティが取り出すすべての値は選択の列から決まり、pbtはケースごとにその列を記録しています。
縮小器はこの列を書き換えます。
1回の取り出しに属する選択を削り、数を下げ、ひとまとまりの選択を前の選択肢へ動かし、要素を並べ替え、書き換えた列から値を作り直します。
候補が現在のケースと置き換わるのは、プロパティがまだ失敗し、かつ列が短くなるか、同じ長さで辞書順に小さくなるときです。
どの操作も進まなくなるか、縮小の時間（デフォルトで30秒）を使い切るまで、操作を繰り返します。

縮小器は値ではなく選択に対して働くので、`Map` や `Bind` で組んだ値のために特別な準備は要りません。
縮小器が下にある選択を書き換え、関数が値を作り直します。
探索の向きは、各生成器が小さな選択から何を作るかで決まります。

| 生成器 | 縮小の向き |
| --- | --- |
| `Int`、`Float64` など数値 | 0、または範囲のうち0に近い端 |
| `IntRangeToward(lo, hi, center)` | 両側から `center` |
| `Bool` | `false` |
| `String`、`SliceOf`、`MapOf` | 要素数を減らし、次に要素を単純にする |
| `SampledFrom`、`OneOf`、`Frequency` | 先頭の値、または先頭の選択肢 |
| `Just` | 縮小するものがない |
| `Custom`、`Map`、`Bind` | 中で取り出す値の向きに従う |

## 探索を導く

表のとおりの最も単純な値が、最も読みやすい値とは限りません。
日付は西暦0年より1970年のほうが考えやすく、時差は720分より数分のほうが何かを語ります。
目標を変える生成器が2つあります。

<!-- snippet: shrinking_test.go#shrinkto -->

`ShrinkTo(g, alts...)` は `g` から生成し、縮小のときに代替の生成器を順に試します。
PropErの `?SHRINK` に相当します。
1990年以降のすべての年で失敗するプロパティは1990を報告します。
まだ失敗する最初の代替生成器の中で、最も小さい失敗する年です。

```text
[pbt] year (ShrinkTo(IntRange(0, 9999))) = 1990
```

`IntRangeToward` は、範囲を下限ではなく中心へ向けて縮めます。
±30分の外で失敗するプロパティは31か-31を報告します。

## 組み上げた値を部品の1つへ縮める

部品から組んだ値は、通常は部品が縮んでも形を保ちます。
3つのスライスの連結は、3つのスライスの連結のままです。
`LetShrink` は選択を1つ追加します。
部品を結合するか、部品のどれかをそのまま返すか、という選択です。
生成時は常に結合し、縮小時にはこの選択を切り替えられるので、組み上げた値が1つの部品へ縮みます。
PropErでは `?LETSHRINK` です。

<!-- snippet: shrinking_test.go#letshrink -->

要素が2つ以上あると失敗するプロパティは `[]int{1, 1}` を報告し、残りの2つの部品は消えます。

## 値をそのまま保つ

`NoShrink` は、縮小器が触れてはならない値に印を付けます。
不透明なトークンや、テスト対象のシステムが形を決めている入力に使います。
縮小しても時間を使うだけだからです。

<!-- snippet: shrinking_test.go#noshrink -->

## 縮小を観察する

`SampleShrink` は、値が縮小するときに辿る道筋を返します。
PropErの `sampleshrink` と同じです。
自作の生成器が期待した向きに縮むかを確かめる最も手早い方法です。

<!-- snippet: shrinking_test.go#sampleshrink -->

実際の実行では、`Verbose()` か `-pbt.v` を付けると、採用した縮小の各ステップが生成した値とともにログに出ます。

## 失敗は同じものに保たれる

ケースは最初にどう失敗したかを記録します。
アサーションの行か、パニックの型と発生位置です。
縮小の間、候補が採用されるのは同じ仕方で失敗するときに限ります。
この規則は、よくある誤りからあなたを守ります。

<!-- snippet: shrinking_test.go#identity -->

最初に失敗したケースが数量3000で、パニックしたとします。
この規則がなければ、縮小器は数量を1000より下げ、101がアサーションに失敗することを見つけて、割引の誤りを報告したでしょう。
パニックは報告から消えてしまいます。
規則があるので、数量は1001まで縮み、報告はパニックを示します。
最初の失敗が割引の誤りだったときは、ケースは101へ縮みます。
どちらにしても、報告はその実行が見つけたバグを記述します。
ステートフルテストは失敗をコマンドと検査の種類で区別するので、あるコマンドの事後条件の失敗が別のコマンドのパニックに変わることはありません。

## 縮小がしないこと

縮小器が到達するのは局所的な最小で、常に全体の最小とは限りません。
自身の尺度で単純になる候補しか採用しないので、いったん大きくなる中間段階を要する小さなケースには届きません。
値の構造が単純な形を隠している場面のために、`LetShrink` と `ShrinkTo` があります。
ケースが縮小している間、サイズパラメーターは固定されます。
時間の上限は失敗1件あたり30秒で、`ShrinkTime` か `-pbt.shrinktime` で変えられます。
