# エージェントでプロジェクトをテストする
<!-- summary: コーディングエージェント向けの作業手順。プロジェクトの契約からプロパティを導き、オラクルと生成器を選び、分布を調べ、長い探索を走らせ、失敗を再実行して切り分け、証拠を添えてバグを報告する。 -->

まず、失敗したときにプロジェクトにとって意味のある、少数のプロパティから始めてください。
プロパティごとに、期待する振る舞いの出典と結果を一緒に記録しておきます。
役に立つ結果とは、プロジェクトの契約と食い違うことを再現でき、その証拠を残すテストが付いているものです。

## 契約を確かめる

テスト対象のコードのドキュメント、公開されている型、既存のテスト、フィクスチャーを読んでください。
プロジェクトが従うと約束している規格も探します。
これらの資料が、妥当な入力、許されるエラー、期待する結果を定めます。
オラクルを選ぶ前に、資料どうしの食い違いを記録しておきます。

基本的な規則からもプロパティが得られます。
妥当なリクエストでパニックしないこと、保存したデータが消えないこと、操作が終わることです。
規則ごとに、その適用範囲を書いておいてください。
例えば、不正な入力でパニックすることがドキュメントに書かれていれば、妥当な入力についての約束には反しません。

バグがあったときに最も害の大きい場所をいくつか選びます。
それぞれについて、入力の定義域、期待する結果、それを求める出典を書き出します。
該当する文があれば引用してください。
契約があいまいなままなら、要件を作り出さずに、決まっていない点を特定します。

## オラクルを選ぶ

**オラクル**は、観測した結果が正しいかどうかを判定する仕組みです。
手間の少ないものから始め、別の種類の誤りを捉えられる箇所に独立した検査を足してください。

| オラクル（手間の少ない順） | プロパティとpbtの道具 |
| --- | --- |
| パニックしない | [NoPanic](04-properties.md#パニック)で型から関数の引数を生成するか、`Check` の中で関数を呼ぶ。パニックはケースを失敗にする |
| 往復 | `ForAll` か `Draw` で値を生成し、符号化して復号し、`Fatalf` で比べる。ドキュメントにある正規化は考慮する。[生成器](01-generators.md)と[形式](10-formats.md)を参照 |
| 参照モデル | 期待する状態の小さなモデルを持ち、[Commandsと事後条件](05-stateful.md)で操作を比べる。ケースごとにシステムをリセットする |
| 各ステップの後の不変条件 | 保存則、順序、所有関係を各コマンドの `Post` で確かめる。`Post` が見るのは `Next` の前のモデル |
| メタモルフィックな検査 | 1つの入力を取り出して変換し、関係する結果を1つのプロパティの中で比べる。例えば、順序に依存しないとドキュメントにある操作は、並べ替えても結果が変わらない |
| 差分の検査 | 取り出した同じ入力を独立した2つの実装に渡し、`Fatalf` で結果を比べる。先に、その入力の定義域で両者の契約が一致することを確かめる |

止まるおそれがあるなら、`go test -timeout` を設定してください。
[Deadlineのコンビネーター](04-properties.md#プロパティを組み合わせる)は、呼び出しが戻った後でしか経過時間を確かめません。
2つの実装の違いは調べるべき証拠であって、どちらかの実装が誤っていることの証明ではありません。

## 契約を突く入力を組む

広い生成器を `Filter` や `Assume` で絞るより、[妥当な入力を組み立てる生成器](01-generators.md)を選んでください。
依存するフィールドには `Bind` を、選択肢の配分には `Frequency` を使います。
既存のテストやフィクスチャーにある境界の値も、生成した値と一緒に入れます。
不正な入力についてのプロパティは分けておき、期待するエラーを明示したままにします。

規格に沿った文字列の入力には、[formatパッケージ](10-formats.md)を使ってください。
プロジェクトが規格の文法全体を受け付けるのか、一般的な形だけを受け付けるのかを確かめます。
Goの型には[Makeかpbtgen](09-types.md)を使い、型で表せない制約はフィールドの上書きで与えます。

ステートフルなコードには、[コマンドの列](05-stateful.md)を生成してください。
個々の呼び出しを独立に試すだけでは、期限の切れたリースや、未処理の仕事を残して閉じたキューのような状態にはまず届きません。
モデルを変えるのは `init` と `Next` だけにし、生成器と検査はモデルを読むだけにします。
外部の状態、時計、資源は、縮小や診断のための再実行も含めて、実行のたびにリセットしてください。

分布は[Classify、Cover、CheckCoverage](02-distribution.md)で測ります。
失敗したときの影響が大きい操作と、境界値のケースにはラベルを付けます。
ある種類のケースが欠けると実験が成り立たないなら、最低限の割合を要求してください。
チェック数を増やす前に、ヘルスチェックの警告を確かめます。
大きな探索で選択の重複が無駄になるなら、`WarnHealth(HealthDuplicate)` を有効にします。

## 段階を踏んで走らせる

まず、変更したパッケージをデフォルトの100チェックでコンパイルして実行します。
統計と警告を確かめてから、ケースの数を増やし、記録したいくつかのシードで試してください。
次のコマンドは、今のパッケージに `TestQueue` という名前のプロパティがあるものとしています。

```sh
go test -count=1 -run '^TestQueue$' -pbt.v
go test -count=1 -run '^TestQueue$' -pbt.checks=10000 -pbt.seed=1
go test -count=1 -run '^TestQueue$' -pbt.checks=10000 -pbt.seed=2
go test -count=1 -run '^TestQueue$' -pbt.checks=1000000 -pbt.budget=30s -pbt.seed=3
```

[Budget](04-properties.md#時間予算)は探索の時間に上限を設けますが、ケースの数の上限で先に終わることもあります。
標的型のプロパティでは `-pbt.searchsteps` を大きくしてください。
どちらの設定も、止まった呼び出しを中断しません。

`-pbt.failures=3` を使うと、1回の実行で複数の原因を集められます。
原因が同じアサーションの位置を共有するときは、安定した[Signatureの名前](03-shrinking.md#失敗は同じものに保たれる)を付けてください。
実行の結果は、コンソールの文字列を解析するかわりに `-pbt.json=runs.jsonl` から読みます。
[Tycheが読むOpenPBTStatsの記録](04-properties.md#機械可読の出力)には `-pbt.observe=observations` を使います。

入れ子の比較のせいでランダムな探索が進まないときは、[CoverageGuided](08-targeted.md#コードカバレッジで探索する)を試してください。

```sh
go test -count=1 -run '^TestQueue$' -cover -coverpkg=./... -pbt.coverage -pbt.checks=10000
```

`-coverpkg` でテスト対象のパッケージを選びます。
カバレッジのカウンターはプロセス全体のものなので、プロパティを単独で実行し、並行するテストを避けてください。
カバレッジによる誘導はオラクルの代わりにはならず、プロパティにはアサーションが引き続き必要です。

## 失敗を調べる

`testdata/pbt` の下の保存したケースは残し、報告の `reproduce:` のコマンドを実行してください。
特定の保存したケースを再実行するには `-pbt.replay=FILE` を使います。
Go、pbt、プロジェクトのバージョンを記録しておきます。
生成器が変わると、保存した選択の意味が変わることがあるからです。
`HealthStale` の警告が出たら、再実行が元の入力を試していると考える前に、その内容を確かめてください。

欠陥を調べやすくなるなら、最小の入力を通常の回帰テストに書き足します。
そのテストが、変更していないコードで失敗することを確かめてください。
逐次のステートフルテストの失敗では、[Causality](05-stateful.md#失敗を招いた手を探す)が、失敗を起こりやすくした手前のコマンドを示唆します。
標本から得た割合は調査の手がかりであって、それだけで原因を確定するものではありません。

| 判定 | 兆候 | 次の行動 |
| --- | --- | --- |
| 本物のバグ | 妥当な入力が、記録した契約と矛盾する結果を返す | 再現手順を残し、食い違いを報告する。実装の修正は、依頼された範囲に限る |
| テストのバグ | 生成器が事前条件を破る、モデルが状態を漏らす、比較がドキュメントにない規則を前提にしている | その誤りだけを正し、理由を記録して、影響するプロパティを再実行する |
| 意図された振る舞い | ドキュメントか既存のテストが、この結果を明示的に許している | 期待を契約に合わせ、ドキュメントにある振る舞いのテストを残す |
| 環境 | 結果が時計、プラットフォーム、サービス、足りないツール、資源の上限に左右される | 依存を記録し、できるなら制御し、ライブラリの欠陥とみなす前に再実行する |

同じ原因を二度報告しないように、関連する既存の調査結果やissueを確かめてください。
制御した再実行で振る舞いが変わっても、元の観測は残しておきます。
不確かな点は、不確かなまま書きます。

## 通過したテストを広げる

通過した実行が示すのは、生成したケースと、実行したアサーションの範囲だけです。
次に何を変えるかは、その実行が残した証拠から選んでください。

- ラベルとコマンドの統計を見て、欠けている形や状態を探します。重みを変えるか生成器に分岐を足し、もう一度測ります。
- `go test -cover -coverprofile=coverage.out` の後に `go tool cover -func=coverage.out` を実行してコードカバレッジを調べます。到達していない経路を、欠けている入力や操作まで遡ります。
- 同じコードに新しいオラクルを足します。往復の検査は、両方向が同じバグを共有していれば通過してしまいますが、独立したモデルならそれを見つけられることがあります。
- `Assume`、`Filter`、明示的な除外が取り除くものを数えます。除外が、重要なケースを隠していないかを確かめてください。
- 長い入力やプログラムを試すには `-pbt.maxsize` を上げ、生成の手間を見張ります。別のシードも試し、その結果を記録します。
- 変更を重ねても、試す入力やアサーションが改善しなくなったら、プロジェクトの別の部分へ移ります。

## 証拠を残す

失敗を消すために、プロパティを弱めたり削除したりしないでください。
誤ったオラクルを直すのは、契約に基づく証拠があるときだけです。
実行を通すために、保存したケースを削除しないでください。
失敗するテストで欠陥を示すまでは、テスト対象のコードを変えないでください。

バグの報告には、試したバージョン、最小の入力、正確なコマンド、期待した結果、実際の結果を入れます。
期待する振る舞いを求めているドキュメントの文も添えてください。
規則の出典が型や規格なら、その出典を示します。
走らせたケースの数、失敗したプロパティ、切り分けの判定、試していない範囲も報告します。
ほかの人が結果を確かめられるように、再現手順を報告と一緒に残してください。
